# AGENTS.md — PipelineK (policy after RESET)

## 0. Authority and scope

- Scope: `Rubentxu/pipeline-kotlin`, active product V2. This file replaces the old testing/harness/documentation regime; do not resurrect it from Git history.
- Effective truth, in order: observed Git/build/runtime behavior; approved product safety, published API and external release/certifier contracts; this policy for repository workflow; concise root README for users. Previous `docs/` and build-root Markdown are historical, not live instructions.
- Keep this file short. No new Markdown anywhere beneath `docs/` or `pipelinek/`. Root README/AGENTS may exist; `examples/` holds the external example plugins, not certification dossiers.
- **A context document aims to stay under 450 lines.** That holds for this file, for the cards of the task manager and for every other Markdown used to gather context (specs, ADRs, the planning packet); the instrument is `wc -l`, because a document nobody reads to the end is a document whose later rules stop being read. When a rule no longer fits, the detail does not go to a new file created to hold it: the rule moves to the place that already carries that same rule — the product's own KDoc, the card in the task manager, the packet outside Git — and the document that grew links to that place. One rule, one home, one link; never a container file invented to gather what no longer fits, and never a file created only to look well organised.
- Before making changes inspect `git status --short`, current SHA, branch, module dependency graph, and actual CLI behavior. Record `PASS`, `FAIL`, `NOT_RUN`, or `BLOCKED` truthfully. An absent test or skipped task is never PASS.
- No hidden dependency on removed documentation, catalogues, certification harnesses or external planners. Git history, a pre-reset annotated tag, and an external archive retain historical evidence without shipping it in the active tree.

## 1. Non-negotiable product constraints

- Preserve V2 behavior, public ABI/wire formats unless a versioned break is explicitly authorized, identity/digests and reproducible release assets. Do not treat an RC as a stable certification.
- Domain and decisions are pure, typed and immutable where practical. I/O, time, files, processes, networking, credentials and persistence reside at named ports/adapters. Invalid input and missing capabilities fail closed with truthful diagnostics.
- Durable replay must never fabricate success or repeat a completed side effect. Preserve run/operation identity, ordered events, exact stdout/stderr bytes and cursors; never log or retain secrets accidentally. No destructive workspace operation may escape the authorized root.
- Prefer meaningful Kotlin ADTs/value objects and small interfaces. No second event, Step, recovery or certification authority; remove dead legacy fallbacks rather than building adapters upon adapters.
- Kotlin/JVM product: follow the Gradle toolchain already declared in the repository. Rust conventions inspire testing organization only; do not add Cargo manifests or Rust code to this Kotlin project.
- **No external dependency for a couple of classes.** A library is a jar in the distribution, a transitive closure to audit, a licence to keep and a behaviour to inherit — paid for in bytes, supply chain and surprise. When what is needed is small and ours to own, it is **copied or implemented in this project**, with the attribution written down. The standing strategy is copy or implement here, not pull in. An existing dependency is not grandfathered either: it stays only if it carries something this project cannot reasonably own — an engine, a file format, an algorithm — and that has to be said explicitly, per dependency, rather than inherited by default.
- No GitHub Actions introduced by default. CI, external certifier and remote publication constraints are external facts, not claims inferred from local success.
- **The product never depends on the state of an account of a third party.** A release gate may not ask whether a key is registered on an account, whether an address is verified there, or what a hosting platform reports as `verified` about a tag: those are facts about somebody else's database, not about the artifact, and a gate that waits for them waits for a human. GitHub is TRANSPORT — where the published bytes live — and never AUTHORITY — who is entitled to sign. Attribution rests on material versioned in this repository: the declaration in `scripts/release/signing-key.conf`, the fingerprint published to the consumers in `RELEASE-SIGNING.md`, and the public key that travels with the release. The instrument is `scripts/check-signing-key-trust.py`, whose seventh row asks whether the fingerprint that signs is the one this repository publishes; `scripts/release/promote-stable.sh` runs that guard as step 1b and refuses the promotion when it is red.
- **The bureaucracy never stops the delivery of value.** A task is delivered when its capability is available and unblocked — not when its paperwork is complete. Documentation is never a precondition: if a rule asks for a document before the value ships, the document is written afterwards or in the same commit when it is cheap, and never in front of the work. Editing a changelog, a roadmap or a receipt that no rule requires is time taken from the delivery; editing what already exists is fine, adding a file to hold a rule that already has a home is not.

## 2. Permanent testing: unit tests, integration tests with mocks, and mutants

- **GATE — every proposal to add a test passes through `delivery-first-testing` first.** Navigate its router `references/navigation.md`, read ONLY the playbook of the announced lens (`change-impact` → `regression-promotion` for a feature; `merge-assurance` for a merge; `integration-assurance` for the integration; `release-assurance` for a release; `failure-triage` for a repeat; `harness-economics` when the harness grew). No ad-hoc second method, no writing the test first and justifying it afterwards. The skill answers in this order and the order is the rule: name the **guarantee** the consumer relies on, name the **observable capacity** it serves, then choose the **cheapest instrument that can fail**. A test is an instrument; it is never the guarantee, and a guarantee that already has equivalent coverage does not get a second one.
- **A green that has never been seen red is not evidence.** Before reporting any new or changed test as passing, break the thing it guards — invert the predicate, remove the branch, restore the defect — and confirm that (a) the mutation was actually applied (read the diff back) and (b) exactly the expected rows go red, with no collateral. A mutation that was not applied proves nothing; a mutation that turns everything red proves the fixture, not the guard. Record the row that turned red. A mutant that SURVIVES is a hole in the guard, and the honest response is to strengthen the assertion that failed to kill it, never to exclude the mutant to make the number look better.
- The inherited Kotlin/Java tests, disabled tests, architectural fitness suites, pluginContractTest, installedContractTest and their internal QA harness have no grandfather rights. Rebuild only tests justified by real behavior or recent defects.
- The permanent Kotlin/Java test sources are each real module's `src/test/kotlin` (matching `src/main/kotlin` package tree) and, where a test needs more than one module at once, its `src/integrationTest/kotlin`. Name a behavior-oriented `XxxTest.kt` next to the corresponding production package; never organize by decision record, date, work item or campaign.
- A **unit test** checks one pure domain rule or isolated application decision. Use JUnit 5 / kotlin.test and lightweight in-memory fakes only where needed. No CLI, subprocess, daemon, network, file-system persistence, Gradle invocation, real clocks, sleeps, Docker/Podman, external credentials, snapshots of private code, or reflective checks of implementation shape inside unit tests.
- An **integration test** composes two or more real modules and runs the REAL seams of the modules it composes, so a wiring mistake between two modules is observable. Most of them replace every effect they would reach outside the process — the filesystem, a subprocess, the clock, the network — with a fake the test owns. The ones that boot the product do not: they use a real child process, a real socket and a real store, and they are DECLARED in the same guard with the reason each one is there. What a test never fakes is the module under test: a test that fakes the module it claims to verify is a unit test wearing the wrong name.
- **There is no E2E, UAT or AAT layer.** No `.pipeline.kts` scenario suite, no acceptance harness, no launcher, no receipt, and no executable end-to-end program is added to this repository again. A behavior that no unit test and no mocked integration test can observe is stated as an honest gap in the change that introduces it — it is not papered over with a scenario program.
- **The layer that boots a product lives in a harness repository, and the record of that work lives in that harness's own board.** A scenario suite, an acceptance harness, a launcher of the product under test and the receipt of a booted run certify the PUBLISHED artifact; the tree that certifies the tree keeps its three legs and holds none of them. Where each harness keeps its work: the certification harness (`pipelinek-release-harness`, in the `Pipelinek-Test-Hardness` workspace) keeps its own cards in the `backlog/` of that repository, and the counterpart of a piece of work is a card in this board that names the other side; the end-to-end harness of the Fabric product (`pipelinek-fabric-e2e`) keeps the execution in its own repository and the card of the work in the `backlog/` of the product it certifies (`pipelinek-fabric`), which does not copy it. **The instrument is `scripts/check-product-boot-layer.py`, and it runs in the first stage of the gate**: the tree may hold no scenario, no launcher, no family map and no init script, and an executable program that the guard's declaration does not name is a failure. The declaration names the gates of the publication that start the published artifact: the compatibility gate, which compares it with the last published one; the acceptance gate of the packaged commands, which asks the archive for the answers a consumer asks it; and the control that proves that gate refuses a broken archive. None of them is part of this gate.
- **A BOOT CHECK — a row that STARTS the PUBLISHED product — is declared, and the gate calls none of them.** A boot check can go red for a reason the code does not have: the machine is busy, the port is taken, the clock of the machine is off. A gate that calls one publishes a verdict about the machine under the name of a verdict about the tree, so the rows that start the PUBLISHED product stay in the tree, they are DECLARED in the same guard with the reason they are here, and they carry the tag `boot-check` that the build excludes when the gate asks for it (`-Ppipelinek.excludeBootChecks`). The certification of the published artifact is the harness's, and it is there that the bytes are certified by their digest. A boot check is recognized by its FORM and not by its name: a row of a test source set that names the product AND starts a process. The tag does not hide one: the form decides, and a row that starts the product is a boot check whether it carries the tag or not. The guard fails on a boot check the declaration does not name, on a declared one that is gone, on a declared one that does not carry the tag, and on a chain that is broken —the gate that does not ask, the build that does not honour the request, and the tag that only one of the three knows. Whoever wants the rows runs the lane without the property: `./pipelinek/gradlew -p pipelinek :pipeline-application:integrationTest --tests '*InstalledProductBoot*'`.
- **The rows that boot the TREE'S OWN product are declared too, and the gate calls them.** The gate certifies THIS TREE, and those rows certify the tree: they compose the modules of this tree and start a real child of them, and no other instrument certifies that composition at every change. The harness certifies the PUBLISHED bytes against a candidate and by their digest, and it never certifies the tree's source; the tree's rows never touch the published bytes. Neither half is a substitute for the other, and the guard holds the two declarations apart: it fails on a row that boots the tree's product and the declaration does not name, on a declared row that is gone, on one that does not boot the product any more, and on one that carries the tag of the published boot checks, because the gate would then stop calling a row that certifies the tree. The price is paid knowingly and is declared: a row that starts a real run measures the machine as much as the code, because the compilation of the script is shared and a saturated machine makes it late, and those rows are most of the cost of the integration lane.
- No shared custom test framework, meta-test, giant base class, golden corpus, mutant registry, coverage-percentage target, source-text fitness, test catalogue or resurrection of `:test-harness` / `:pipeline-architecture-tests`.
- Work loop: implement a discriminating failing test for changed behavior when useful, implement smallest fix, refactor; execute only affected module/test while editing. A trivial DTO/getter/boilerplate change does not mandate a test.
- Permanent test count is driven by risks, NOT by test-to-production parity or a file quota.

## 3. Mutation testing: the mutants that must die

- **The mutants are the third leg of the gate, and they are SELECTIVE.** `pitest` runs on the modules that declare it, over the seams they name: the replay kernel, the durable decision kernels, the codecs and the policies that decide. It is not a global sweep, and a mutation score is never a gate: a percentage is not a guarantee, and a high score does not certify a behaviour.
- **A surviving mutant is a defect in the test, not a defect in the product.** Investigate it, and either strengthen the cheapest assertion that failed to kill it or record why the mutant is equivalent or unviable. Excluding a mutant to improve the number is the failure this rule exists to prevent.
- **A mutation score never justifies changing the product.** The product is not modified to satisfy a mutant; the assertion is. The only exception is a mutant that finds a REAL defect, and then the defect is fixed on its own merit, as a defect.
- The mutator set, the target classes and the target tests are declared per module, next to the module's own tests, and the declaration says WHY that seam and not another. A module that names a target with no reason to name it names nothing.
- Pitest is a JVM tool that mutates bytecode and reruns the selected tests. When the tool, the runner or a JDK it needs is unavailable, the run is `NOT_RUN` and the reason is written down; it is never installed silently to make a green appear.

## 4. The gate: unit tests, integration tests and mutants

- The gate is ONE entrypoint: `scripts/verify-all.sh`. It runs the checks that read only the tree, the build with its static analysis and its API compatibility check, the review of the published reference, the unit tests, the integration tests, and the mutants. It is not a test framework, has no registry, no service, no database and no tests-of-tests, and it stops at the first failing stage so a red run names the stage that is red.
- **The gate calls no layer that boots the PUBLISHED product, and it says so instead of letting it be assumed.** The harness layers are foreign to this gate: a harness certifies the published artifact and keeps the record in its own board, and this gate neither runs it nor inherits its verdict. The first stage checks that this tree holds none of that layer, and that every boot check it does hold is DECLARED and excluded from the lanes, so the statement and the tree agree. The rows that boot the TREE's own product are the other half of the split: the gate calls them, they are declared in the same guard, and the text says so.
- **A verdict line carries the evidence of what ran.** It states `tests=executed:<n> failed:<n> skipped:<n> rewritten:<n> read:<n>`, the same shape for `integration`, `mutants=run:<n> killed:<n> survived:<n> rewritten:<n> read:<n>` and `reference=contracts:<n> unresolved:<n>`, plus the elapsed seconds of every stage. `rewritten` counts the reports THIS run wrote; `read` counts the ones it inherited from an earlier invocation over the same inputs. A leg that did not run says `NOT_RUN`, because a silent field reads like a zero, and so does a stage that never started: it says `NOT_RUN` and not zero seconds. The difference between this run and the full gate has to be INSIDE the line, not beside it.
- **A red run prints a verdict too.** The line names the stage that is red and the evidence of that stage — `FAIL ... stage=2 reason="the published reference" reference=contracts:7 unresolved:1` — because the stage that names the failure is the stage the reader has to open. A run that stops with a message and no verdict leaves the reader to guess what was measured before the failure.
- **The gate does not re-measure what it already knows.** Gradle re-runs a test task when its inputs changed and skips it when they did not; the gate does not override that. A lane whose sources did not change is UP TO DATE, and its report is the measurement of this tree — re-running it would spend the delivery's time and would measure nothing new. The verdict separates the rewritten reports from the inherited ones, so an inherited report is never passed off as a measurement that happened now.
- **A filtered run is SUBSET and says so.** Any filter switches the verdict to `PASS (subset)`, prints `filters in effect:` and reports the counts from THIS run only. A stage filter is a filter: `--stage 2` measures the tree and the build and the reference, and it is not the whole gate. A scoped run that ends with the same line as the full gate is a line that gets quoted as "the gate passed" while having measured one module.
- **The gate runs every TEN tasks of the backlog board, and not on every change.** The board is the unit of delivery: ten implemented tasks are the batch that gets certified, and the gate is what certifies it. The gate is not part of every iteration, and a delivery that stops at ten tasks without running it has delivered an uncertified batch. **THE BATCH EXISTS TO DELIVER, NOT TO CERTIFY**: a tenth task that is certified is worth less than a tenth task that exists.
  - **The batch is counted by the MERGE.** The counter starts at the merge that closed the last batch — the merge named in the card that paid the gate — and is read from the history (`git log --oneline --merges <last-batch-merge>..main | wc -l`), not from the memory of the agent: a card that is written but not merged is not a closed task, and a merge with no card is not counted either.
  - **INSIDE a batch, a task is verified by the lane of the module it touched, and by nothing else.** The instrument is the Gradle task of that module — `./pipelinek/gradlew -p pipelinek :<module>:test`, plus `:pipeline-application:integrationTest` when the change adds or moves an integration row — together with the discipline of section 2 (a green that has never been seen red). The gate does NOT run between two tasks: it re-measures the whole tree, and a tree certified ten times in a row pays the delivery ten times for one fact.
  - **The TENTH task pays the gate, complete and without filters**, over the merge that closed it and with a clean tree; that verdict is the receipt of the batch.
  - **THE EXCEPTION IS NAMED, not felt.** A change that touches a seam EVERY row walks —the DSL, the compiler or the engine— pays the scoped gate of the module it touches (`--stage 3 --module ':<module>'`) instead of the lane alone, because that seam is what the integration rows of the whole tree run on. The reason is written in the card of the task, and the exception is per change: it does not become the rhythm.
- **The review of the documentation is a leg of this gate, and not a second gate.** The reference of the published contracts is generated again on every run and analysed, and a KDoc link that names a symbol the reader cannot open fails the run: the reference is the document a third party reads to learn the API, so a broken link in it is a broken promise in the product's own words. The instrument is `scripts/check-published-reference.py`, it runs in the stage that builds, and it stands on its own — run by hand over the tree you are working on, it answers the same question the gate answers. There is no second entrypoint, no service and no state file: the receipt of the review travels with the change, in the commit or in the card of the task manager.
- **The review is forced, and that is the price of a real measurement.** The generator holds no `failOnWarning` of its own, and a generation the build finds up to date emits no warning at all: counting the warnings of a held generation would report zero unresolved links whatever the tree says. The reference is therefore generated again for every run of the leg, and the count in the verdict is a number this run earned.
- **A change that only touches the documentation pays for the documentation and nothing else.** It is certified by the stage that carries the review — `--stage 2` — and it pays neither the unit tests, nor the integration tests, nor the mutants. No rule requires an integration test for a change that only touches the documentation, and adding one would be the third mistake this section names.
- **The inner loop is cheap, and it says what it cost.** `--stage` and `--module` narrow the work to the part that changed, and `--list` answers what the gate would run without running any of it. A change that touches one module is certified by that module's lane; the whole gate runs when the whole tree is what is being certified — and WHEN that is happens is decided by the batch above, not by the caution of the moment.
- **A filter that matches nothing exits nonzero.** Selecting zero is a mistake in the invocation, never a green.
- **A module with a test source that produces no JUnit XML FAILS the gate, and so does a module whose reports declare no executed test.** Gradle 8.14 exposes no `failOnNoDiscoveredTests` property, so a `Test` task over an empty or undiscovered source set reports SUCCESS over zero executed tests. The gate reads the XML reports and refuses that green; the guarantee lives in the gate script, not in the build files. The counters are read by GRAMMAR: `scripts/read-junit-reports.py` parses the root element of the report and reports the counters the root DECLARES. A counter that is absent declares nothing, so a report that declares no counter is refused, naming the file and the attribute, and a lane whose reports declare no executed test is refused too. The guard is armed on the MEASURED count and not on the presence of files.
- **The wall clock is published, not budgeted.** The gate prints the elapsed time of every stage, so the price of the run is visible instead of measurable only by hand. There is no time budget to breach and no level to certify: a run is either the whole gate or a stated subset of it, and its cost is a fact the reader can see.
- **The LOC census counts what is left.** The permanent unit tests, the integration tests and the repository's own verification scripts count as VERIFY_LOC; the active production source counts as PRODUCT_LOC. The census reads `git ls-files`, so it counts tracked files only: measure on a committed tree, never on a dirty one.
- **The static analysis has to see the serializer of every type a module declares.** The `kotlinx.serialization` plugin generates a `serializer()` function in the companion of every `@Serializable` class, and detekt 2.x resolves types in a standalone Kotlin Analysis API session that never registers the plugin's services. So `T.serializer()` on a type the analysed module declares is invisible to the analysis, and an analysis that cannot resolve a type cannot tell a real finding from an invented one — the gate then tolerates findings it can no longer judge. The serializer of a type a module declares is therefore obtained through the reified lookup `kotlinx.serialization.serializer<T>()`, which the analysis resolves and which the plugin rewrites into the very same generated serializer; the companion form stays for a type of ANOTHER module, because there the analysis sees the compiled class. **The instrument is `scripts/check-serializer-visibility.py`, and it runs in the first stage of `scripts/verify-all.sh`**: it fails when a source set calls `T.serializer()` on a type that same source set declares.
- Integration/release: full local verification over the final SHA; distribution identity/checksums/ABI and any required independent certifier gate. The published archive is asked the commands a consumer asks it — the catalogue of the steps, the card of one step, the offer for the steps of Jenkins, the usage and the identity of the bytes — and the gate that asks them runs its own negative control, because a gate that has never refused a broken archive certifies nothing. No stable promotion based on unit tests alone. If a mandatory external verifier is unavailable, record `BLOCKED_EXTERNAL`, not PASS.
- **Reading a large file is not the same as reading it whole.** A file over 30KB is never read end to end: ask for the part you need. `ctx outline <file>` returns the file's structure; `ctx symbol <file> <line> <col>` returns one symbol's code; `ctx usages <symbol>` returns who uses it; `ctx section <file> <pattern>` returns one section of a document. Use them before opening any file over 30KB and before a recursive `Grep` over the tree. `ctx` tries **CogniCode first** and falls back to **codegraph** where CogniCode cannot reach; the engine that answered is announced on stderr. This changes how much is read, never what is decided: the policy and the gate are this file's.

## 5. Documentation, cleanup and publication

- Delete ALL tracked `*.md` beneath `docs/` and `pipelinek/` with Git-aware deletion; do not silently recreate them, even as receipts, historical dumps or pseudo-specifications. Do not delete non-Markdown product resources blindly: check runtime/build consumers first.
- Archive useful historical material in the immutable pre-RESET Git tag/external archive, not a new tracked docs tree. Remove/correct references in build scripts, README, source KDoc, distribution scripts and CI hooks to deleted locations. Documentation that users need belongs in a short root README or inline Kotlin KDoc, not a growing markdown hierarchy.
- Keep user-facing examples and necessary public product modules; `:pipeline-event-harness` currently serves the `pipeline events verify` product command and must not be deleted merely because of its name. Remove only QA-only modules after identifying consumers.
- Deliver atomic commits by demolition/build cleanup/new tests/gate/policy. End with integrated, pushed branch and RC only where release gates genuinely pass; publish exact SHA/digest and record any blocked external verdict. Do not claim verification you did not run.

## 6. What a comment must say, and what must be able to fail it

- The code explains HOW it works, the documentation explains the CONTRACT it offers, and the history of the work lives in Git and in the task manager. A comment that names WHO asked for a change tells the reader nothing the history does not tell better, and it stops being readable the moment the tree is read without that history.
- **A comment carries no administrative provenance**: no ticket or issue identifier, no commit hash, no pull-request reference, no name of a working document that does not travel with the tree, no administrative label, no coordinate of a plan, no person's name, and no narration of a past implementation. Each of them points at a fact the reader cannot open, so the fact has to be in the comment itself.
- **A comment may carry what the product promises**: `RunId`, `OpId`, `traceparent`, a published vulnerability identifier, a normative reference, a wire or file-format name. The difference is not the prefix and not the capitalisation; it is whether the reference belongs to the CONTRACT — whether the code would be wrong if the reference were wrong.
- **Every rule names the instrument that can fail it, or says that it has none.** `scripts/check-comment-provenance.py` fails on the shapes it recognises: ticket, section, commit hash, working-document name, administrative label, plan coordinate, a reference to something outside the tree (an issue, a pull request, a merge request), an attribution to a person, and a narration of a past implementation that names a symbol the tree no longer contains. It reads tracked `.kt`, `.kts` and `.sh` under the product tree, the examples and the scripts; it does not read Markdown. Every vocabulary added after the tree was MEASURED instead of guessed at is closed, and its exception list — with a reason per exception — is written down in the guard itself; the measured false positives over the tree are zero. **A narration that names nothing has NO mechanical instrument**: the tree carries hundreds of past-tense sentences that are not provenance at all, so the rule needs the dead symbol to discriminate; for a narration without a name, review remains the instrument, and saying so is part of the rule. The Detekt documentation rules are added progressively, and only over the part of this section that is mechanically decidable. This prose is outside both guards and is governed by review.
- **This file obeys the rule it states**: it names the forbidden shapes without reproducing them, so applying the guard's own patterns to this file finds nothing. A policy that failed its own check would be worse than no policy.
- **KDoc earns its place on the public API**: a supported public type or function states what it guarantees, what it refuses, and what it does with invalid input. An empty KDoc written only to satisfy an analyser is worse than none, because it buys a green with a lie. Private helpers need no KDoc unless they hold a non-obvious invariant.
- **A contract KDoc is written this way.** The opening line states the guarantee and does not restate the name of the type; the lines that follow say the precondition it imposes, what it rejects, what it does with invalid input, what effects it has, and what the consumer may take for granted. Here is one, from the published surface:

  ```kotlin
  /**
   * The store was reachable and holds nothing under that name.
   *
   * The answer is about the credential, not about the store: the name is
   * wrong or the credential was never created. A caller that reads this as a
   * broken store is diagnosing the wrong thing.
   */
  data class NotFound(val id: String) : BasicCredentialResolution
  ```
- **That rule has an instrument, and it runs in the gate.** `scripts/check-kdoc-coverage.py` locates, in the sources of the module that publishes each contract, the types its `.api` names, and the first stage of `scripts/verify-all.sh` fails when one of them carries no KDoc: the published surface is the surface a third party programs against, and a type whose contract cannot be read is a type whose contract does not exist. The types the compiler writes —the file facades, the `DefaultImpls` holders, the companion the serialization plugin adds— are listed and measured by nobody.
- **The links of that KDoc have an instrument as well.** The reference of the published contracts is generated and analysed on every run of the gate, and a link that names a symbol the reader cannot open fails the run. The coverage rule asks whether the contract is written; this one asks whether the reader can follow it.
- **A comment that explains a non-obvious invariant stays**, and that is the point: the ban is on provenance, not on explanation. Explain why a branch exists, why the order of two operations matters, why a value may not be cached.
- **Three mistakes to avoid**: documenting every private method; adding a comment to silence an analyser; adding an integration or end-to-end test for a change that only touches documentation. None of the three fails the product, and all three cost the next reader.
- **When the contract changes, the documentation changes in the same commit.** A commit that changes what the product guarantees and leaves the KDoc promising the old thing is a defect, not an unfinished task.
