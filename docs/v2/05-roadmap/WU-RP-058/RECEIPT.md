## What this spike proves

ADR-0093 route B (suspend structured DSL) can be realized **without**:

- touching `Main.kt`, `PipelineRun`, `PipelineOrchestrator`, or any canonical
  durable spine piece;
- introducing a new public `StepSpec` subtype;
- introducing a new public `StepKey`;
- routing on concrete StepKey / stepName;
- breaking the requirement that the canonical spine owns durable truth.

The spike is an **isolated module** that defines:

1. A typed, closed ADT family for stage-scoped runtime-returning calls
   (`StageOp`, `SuspendCall`, `SuspendOutcome`, `StagePlan`, `Executed`,
   `LexicalOrderSpec.Result/Reason`).
2. A pure builder (`StagePlanBuilder`) that constructs plans without I/O.
3. A narrow runtime port (`SuspendRuntimeFacade`) — five typed methods,
   no `Any?`, no flag bag — that the spike never wires to a real
   coordinator or scripting host.
4. An interpreter (`StageScopedFrontend`) that is exhaustive over `StageOp`,
   does NOT re-execute eager ops, and produces an immutable replay-stable
   trace (`Executed.WithSuspend`).

## What this spike does NOT do

- It does not connect to `Main.kt` or to the canonical
  `CanonicalDurableRunCoordinator`. That wiring is a separate work item,
  gated by `INITIATIVE_LPR_001 §2.4`, and is explicitly out of scope.
- It does not change any public DSL, public API, public Step, or
  production contract.
- It does not introduce a new failure mode for the canonical spine: the
  spike is unreachable from `pipeline-application` because it is not on
  that module's classpath (see "Isolation" below).

## Conclusion

The spike is sufficient evidence that ADR-0093 route B is **architecturally
sound** in isolation. It does not pre-authorise production wiring — that
work is gated by:

- `INITIATIVE_LPR_001 §2.4` (release-publication exception);
- an explicit `StepSpec` extension (only if production goes that way);
- reconciliation with the still-open canonical release gate.

The spike is intentionally **frozen** at this SHA. Any future production
wiring that uses the spike's ADT family must add the production adapter
**as a new module**, must NOT mutate any of the spike's files, and must
update `WU-RP-058` receipts accordingly. If the spike's design is found
wanting in production, the spike is rewritten — production code never
references the spike's internal types directly.

## Open questions for ADR-0093 follow-up (NOT blockers for this spike)

1. Does the production adapter live in `:pipeline-application` (coordinator
   side) or in a new `:pipeline-spike-adapter` module? Spike design is
   agnostic; either is viable.
2. How does `StagePlan` integrate with the existing `StageScope.steps`
   collector? The spike replaces the collector only if route B is
   adopted; current shape is "parallel path that does not touch
   `StageScope`".
3. Does `suspend` need to thread through coroutines? The spike avoids
   coroutines entirely (pure data + dispatch loop). Future adoption may
   need to decide; the spike deliberately does not pre-judge.
