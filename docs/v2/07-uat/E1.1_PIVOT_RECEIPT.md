## Outcome

E1.1 **PIVOTS**: the original plan was to add `core.junit` as a new
core Step. Operator feedback during T3 intake (2026-09-20T09:17:44Z)
corrected the cycle: `junit.results` is already a certified
OFFICIAL_PLUGIN Step (F5.2, `v2/pipeline-step-sdk/junit/`). Adding
`core.junit` would be a **second implementation of the same
capability**, which violates the cycle's authorization table
("Reimplementar funcionalidades existentes" → forbidden) and the
project's hexagonal rules (single authority for a capability).

The pivot moves E1.1 forward as `core.artifact.query` (originally
E1.2). The new first increment is the **artifact query bridge** —
the gap that genuinely remains in the catalog.

## Why this pivot is correct (evidence)

The verification executed at 2026-09-20T09:18Z (no code changes;
read-only inspection) confirmed:

| Need the cycle planned for `core.junit` | Already covered by `junit.results` |
|---|---|
| Parse JUnit XML into typed summary | `JUnitReportParser` (SAX, XXE-hardened, streaming) |
| Typed output envelope | `JUnitReportSummary { tests, failures, errors, skipped, durationSeconds, reportPath }` + `JUnitResultsOutput` carrier |
| Failure semantics on parse errors | `JUnitReportParseException` → USER kind, fail-closed |
| DSL façade | `StageScope.junitResults(reportPath, workspaceRoot, failOnFailure, maxReportBytes)` |
| StepKey + discovery | `JUnitResultsKey.VALUE = "junit.results"` + `JUnitStepDefinitionContributor` (ServiceLoader) |
| Capability declaration | `junit.operations` (admitted via `StepCapabilityAccess`) |
| Contract test | `F5_2_JUnitStepContractTest.kt` + `JUnitWorkspaceIsolationTest.kt` |
| End-to-end execution | WU-LPR-062 ran a real `checkout → build → test → junit.results` flow end-to-end (per `TESTING-STATE.md` snapshot 2026-09-13) |

E1.0.T2 inventory was correct in noting that **no `core.*` step
called `core.junit` exists**, but it failed to verify whether the
case was already covered by the **SDK plugin** `junit.results`. The
project's hexagonal architecture intentionally puts some steps in
`pipeline-application` (core, in-tree) and others in
`pipeline-step-sdk/<name>` (official plugins, out-of-tree but
in-org). The catalog authority is the StepKey, not the module.
