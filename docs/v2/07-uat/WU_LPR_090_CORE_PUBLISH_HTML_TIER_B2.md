## Executive summary

`core.publishHTML` (Jenkins `publishHTML` step, registry-parity) is the **20th
CERTIFIED core Step** and the **15th CERTIFIED in Tier B**. It adds the
`HtmlReportPublished` 51st `DomainEvent` and the `PUBLISH_HTML_OPERATIONS_CAPABILITY`

event counts, not entry content, so the bug escaped. Fixing the bug in
LPR-090 retroactively improves LPR-089; the LPR-089 fixture now decodes
its `entries` array correctly when read back via the CLI.

## Latent bug discovered + fix (in-scope for this WU)

### Symptom

G7 canary stdout showed `entries":[]` for `HtmlReportPublished` despite
the `SqliteEventStore.eventsFor()` returning the correct raw JSON.
Tracing showed the inner array of objects was not extracted.

### Root cause

`JsonEventLog.extractJsonArray` (file
`v2/pipeline-events/src/main/kotlin/dev/rubentxu/pipeline/v2/events/JsonEventLog.kt`,
function `extractJsonArray`) walked forward from the position right
after the marker `"$fieldName":[`, tracking only `bracketDepth`
(`[`/`]`). The marker already consumed the opening `[`, so the walk
started at `bracketDepth = 0` with the cursor on the first character of
the first object in the array. For an array of objects
`[{...},{...}]`:

1. `{`, `}` (first object) → bracketDepth unchanged (0)
2. `,` (separator) → no change
3. `{`, `}` (second object) → bracketDepth unchanged (0)
4. `]` (closing bracket) → bracketDepth = **-1**
5. End of string; the depth never reached 0 from below → `extractJsonArray`
   returned `null` → caller interpreted as "empty list".

`braceDepth` tracking was added in an earlier iteration of this WU but
the `bracketDepth` initial value remained 0. The combination produced
the bug: even with braceDepth correctly tracked, the `bracketDepth == 0`
gate that determines "we found the matching close-bracket" was never
hit (because we start at 0 and decrement to -1).

### Fix

`bracketDepth` initial value is now `1` (the opening `[` was consumed
by the marker itself). The walk decrements on `]`; when `bracketDepth
reaches 0`, we have found the matching close. `braceDepth` continues to
guard against `[` and `]` inside string fields or nested arrays.

This is the canonical fix; the same call path is used by all
array-of-objects `DomainEvent` payloads, including
`StashCreated.entries` / `StashRestored.entries` from WU-LPR-089 (the
prior WU's closure receipt only counted events, not entries, so the
bug escaped detection there).
