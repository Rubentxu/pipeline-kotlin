The Forms F probes are the empirical capture that closes the operator's
literal-type distinction. The byte-level truth:

F1 (sh with raw triple + \${USER}) — COMPILE FAILS.
   PHASE_3_COMPILE=FAIL ERROR:Unresolved reference 'USER'.:L1:C53
   The Kotlin compiler, on seeing `"""\${USER}"""`, does NOT interpret
   `\$` as an escape inside the raw triple, so the source remains
   `${USER}` from Kotlin's point of view and Kotlin tries to expand it
   as a template — failing because `USER` is not in scope.

F2 (sh with raw triple + ${'$'}USER) — COMPILE OK.
   PHASE_3_COMPILE=OK
   `${'$'}` evaluates to literal `$` in any literal type (raw or
   ordinary). The compiled string contains the 5 bytes `$USER`. This
   is the only safe form for a `$IDENT` reference inside a raw triple
   quoted `"""..."""` literal.

F3 (sh with raw triple + \$USER) — COMPILE FAILS.
   PHASE_3_COMPILE=FAIL ERROR:Unresolved reference 'USER'.:L1:C52
   Same diagnostic column position as F1 (C52 vs C53 difference is one
   byte — the missing `{`). Kotlin sees `\$` as two literal bytes in
   raw triples, NOT as an escape; the next chars form `$USER` and
   Kotlin tries to expand as a template.

CONTRAST WITH ORDINARY "..." LITERAL (Forms A..D):
   Form C (ordinary "..." + \$USER) → OK. The backslash IS escape in "...".
   Form D (ordinary "..." + \${USER}) → OK. \$ + {USER} survives intact.

The trap is literal-type-specific. Inside raw triples, the backslash
does not escape `$`, so any author who carries an ordinary-string
escape habit into a raw triple will hit a compile error rather than a
bash error. This is at least as good as the failure mode in "..."
literals — Kotlin refuses to compile before bash sees anything.

WHAT THE CONTRACT DOCUMENT SAYS (must be revised at T8):
   SH_VAR_SCOPE_CONTRACT.md §2 row "raw triple \${USER}" claims the
   backslash neutralises the template. Phase 3 above contradicts that

   raw triples. The contract must:

   - mark `${'$'}...` inside raw triple as the SAFE form;
